## 一、更真实环境的设置(比论文更贴近部署)

论文只测两个"刻意挑选"的窄 agent(EHRAgent=模板化医疗 SQL;RAP=Webshop),内存是**模板化基准问题**,
且**无任何防御、无会话隔离、静态内存**。我构造了一个更真实的环境:

- **agent**:通用"个人生活助理",长期记忆 = **120 条自然、跨领域、带真实 PII 的私密用户消息**
  (重病诊断/债务/官司/离婚抚养/心理治疗/移民/性健康/成瘾/生育……,全部虚构姓名与数字)。
  这比 MIMIC 模板问题(`"tell me patient 76005's sex"`)真实得多。
- **检索**:编辑距离 top-4(论文中最强配置)。
- **攻击**:15 条 MEXTRA 风格基础攻击 + 8 条**伪装/自适应**攻击(把"提取"包装成 UX审计/翻译/找错别字/
  无障碍朗读/markdown 表/情感标注等无害任务,正是论文 §C 声称的"伪装成无害")。
- **真实部署会有的条件**:C1 一行系统护栏、C2 廉价 LLM 检测器门、C3 per-user 会话隔离;并跨 3 个 backbone。

## 二、真实环境实验结果(这是论文最经不起推敲的地方)

### 结果总表

| 条件 | EN(私有 query 泄漏) | CER | 解读 |
|---|---|---|---|
| C0 基线(无防御)DeepSeek-V3.2 | 5 / 5 | 0.73 | 攻击生效,吐出真实 PII |
| C0 基线 Qwen2.5-72B | 5 / 5 | 0.93 | 机制泛化 |
| C0 基线 DeepSeek-V3 | 5 / 5 | 0.93 | 机制泛化 |
| **C1 一行系统护栏** | **0** | 0.0 | 单行规则 100% 阻断 |
| **C2 廉价检测器门** | **0** | 0.0 | 全部拦截 |
| **C3 会话隔离** | **0 / 120 私有可达** | — | 结构性消解 |
| C0 伪装攻击(无防御) | 7 / 7 | 1.0 | 伪装后照样全提取 |
| **C1 护栏 vs 伪装攻击** | **0** | 0.0 | 伪装仍被全挡 |
| 检测器 vs 基础攻击 | **TPR=1.00 / FPR=0.00** | — | 完美可分,零误报 |
| 检测器 vs 伪装攻击 | **TPR=1.00** | — | 8 个伪装全部识破 |

### 由此得到的三条核心反驳

**反驳①:论文"防御难以奏效"的说法无实验支撑且基本错误。**
论文 §C 只用一句话打发防御("攻击 prompt 可伪装成无害,使过滤失效;改写也无法完全消除"),**零实验**。
实测:**一行**系统 prompt 护栏就把 EN 从 5→0;一个**廉价**单 token 检测器以 TPR=1.0、FPR=0.0 挡下全部攻击。
连论文所说的"伪装成无害任务"的自适应攻击(UX审计/翻译/无障碍…),检测器**仍 100% 识破**、护栏**仍 100% 阻断**。
即:论文宣称的"urgent need for memory safeguards"被自己未做的实验夸大了——naive 防御已足够挡住论文的 naive 攻击。

**反驳②:威胁完全依赖"共享内存池 + 无会话隔离",而这正是现代 agent 的标准做法的反面。**
C3 实验:一旦记忆按用户隔离,攻击者检索只能看到自己的记录,**120 条私有记录 0 条可达**,攻击被结构性消解。
论文在 Limitations 里承认这点,却轻描淡写为"future work";实际上**会话/用户级隔离不是缓解、而是直接消灭**这个威胁。
论文把一个"配置错误才会发生"的问题,包装成"LLM agent 的内在隐私风险"。

**反驳③:危害真实但被"无防御"前提放大。**
C0 下模型确实吐出真实 PII(如 `"Robert Kim 精液分析 1500万/ml"`、`"和 Alex Garcia 染上疱疹"`)——所以**无防御时危险是真的**。
但这恰恰说明:论文衡量的是"一个没有任何护栏、共享所有用户记忆、内存还静态不变的 agent"的脆弱性,
这是一个**稻草人式的最坏配置**,而非"代表性 agent"。

> 补充观察:同质化的基础攻击 prompt 导致检索高度重叠(15 条攻击只检索到 5 条唯一记录,RN=5)。
> 即论文的高 EN/RN **严重依赖 Iadvan 的多样性工程**;缺了它,检索集塌缩、泄漏量骤降。

## 三、论文潜在问题系统清单(分类,含严重度)

### A. 威胁模型不现实(★★★ 最致命)
1. **共享内存、无会话隔离**:整个攻击假设所有用户的 query 进同一个可被任意检索的池子。现代 agent(ChatGPT memory、
   Claude projects、企业 RAG)普遍 per-user / per-session 隔离。C3 实测:隔离后泄漏=0。(论文 §2 / Limitations)
2. **静态内存假设**:论文明确"static memory setting, stored records remain unchanged"。真实内存动态写入——攻击者
   自己的探测 query 会被写进内存、改变检索分布、并稀释/淘汰旧记录。论文回避了动态性对攻击稳定性的破坏。(§4.1)
3. **攻击者能力过强**:需对**同一静态池**发 30–50 次精心构造查询且不被限流。真实系统有 rate limiting、异常检测、
   内存淘汰,使"累计 R 并集"的前提难成立。
4. **"拿到 query 就能复现 response"未经验证**:论文称"once user queries are obtained, the corresponding agent
   responses can be easily reproduced",但全文**只验证 qi(问题)子串出现,从不验证 si(解/响应)被提取**。
   这是一个未做实验的强论断。(§2.2)

### B. 防御被系统性低估(★★★)
5. **缓解措施零实验、且实测可被一行防御击败**(见上反驳①)。(§C)
6. **攻击 prompt 直白异常、极易检测**:实测 TPR=1.0/FPR=0.0,连伪装版也被识破。论文从未量化攻击的"隐蔽性"。
7. **更安全对齐的模型可能天然免疫**:复现中 DeepSeek 已会**自发拒绝**("I don't have access to previous
   examples");论文自己 Table 3 里 **Llama3-70b CER=0**。攻击成败强依赖 backbone,不是"LLM agent"的普遍属性。

### C. 评估方法学缺陷(★★★)
8. **两个 agent 评估口径不一致**:EHRAgent 是**自动逐条精确子串**(`evaluation.py`);RAP 是**半手工**——人工标注
   `memory_failed_indexes`,再把非失败 prompt 的 top-3 检索 ID **全部**算已提取(`成功⇒全提取`)。
   所以 RAP 的 **EN≈RN 是方法学人为结果**,且**无法用自动 pipeline 复现**(我严格口径下 RAP EN=0,宽松也仅论文的 ~1/4)。
   (`EHRAgent/attacking/evaluation.py` vs `RAP/attacking/evaluation.ipynb`)
9. **"提取"判定过松**:retrieved query 只要作为**子串出现在输出任意位置**即算"提取",不区分"模型主动泄漏"与
   "被动回显 few-shot 块"。模型哪怕无意复述上下文也被计为"隐私泄漏"。
10. **硬编码脚手架污染指标**:复现发现 EHRAgent 的"泄漏"里常混入**系统 prompt 的公开示例问题**
   (`comp-oth vasc dev/graft`、`tpn w/lipids patient 2238`…),这些是**非私有**内容,但 EN 把"泄漏私有记忆"与
   "复读公开脚手架"混为一谈;论文仅在 k=1 含糊承认(Table 9 脚注),未从指标中剔除。
11. **无误差棒 / 单次 run**:论文用 temp=0 当确定性,实测 DeepSeek temp=0 **非确定**(同一 prompt 三次三种输出;
   我两次独立 run 的 Table 1 EN=50/55)。所有点估计无方差,趋势图的细小差异不可信。

### D. 泛化性 / 鲁棒性被夸大(★★)
12. **只覆盖"把原始记忆明文塞进 few-shot 上下文"的范式**。对**摘要式记忆 / 只回传向量 ID / 工具中介记忆 /
   先检索后摘要**的 agent 完全不适用。论文"general agents"是过度泛化。
13. **嵌入模型敏感**:cosine 结论随 embedder 漂移。复现中换 bge-m3 后,**"advanced cosine > basic" 翻转为
   basic > advanced**,且 cosine 的 CER(0.27–0.60)远低于编辑距离(0.77–0.90)。检索依赖的结论脆弱。(Table 2 / Fig 4b)
14. **backbone 依赖**(见 #7):同一攻击在不同模型上 CER 从 0 到 0.93,"LLM agent 普遍脆弱"言过其实。

### E. 工程 / 复现性问题(★)
15. 公开仓库 config 里 API key 是占位符、路径硬编码 `XXX/`;RAP 预生成查询是 `{"instructions_list": [...]}`
   的非常规结构;`run_attack.py` 默认 `memory_size=500` 与论文正文 200 不一致;多处循环被注释。**开箱难复现**。
16. 论文正文与代码默认值不完全对应,部分图(Fig 4)数字密集叠印、难以逐点核对。

## 四、严重度小结(供判断)

| 维度 | 论文主张 | 实测/分析结论 | 严重度 |
|---|---|---|---|
| 防御难度 | 防御可被绕过,需紧急对策 | 一行护栏/廉价检测器 100% 挡住,连伪装攻击也挡住 | ★★★ |
| 威胁普遍性 | LLM agent 内在风险 | 仅在"共享内存+无隔离+静态"最坏配置下成立;隔离即消解 | ★★★ |
| 评估可信度 | EN/RN 等量化脆弱性 | 两 agent 口径不一致、判定过松、含非私有内容、无方差 | ★★★ |
| 泛化性 | 适用一般 agent | 仅适用"明文记忆进上下文"范式;强 backbone/embedder 依赖 | ★★ |
| 复现性 | 有开源代码 | 数值整体可复现(编辑距离),但 RAP 半手工不可自动复现、工程粗糙 | ★ |

**总判断**:MEXTRA 揭示的现象**在"无防御 + 共享记忆"的实验配置下是真实的**,作为"提个醒"有价值;
但论文的**两个核心叙事——"难以防御"和"LLM agent 的普遍/紧迫风险"——都被本次真实环境实验直接削弱**:
廉价防御足以阻断、会话隔离足以消解、强 backbone 已部分免疫、量化指标本身偏向攻击且口径不一。
更恰当的定位是:"在缺乏会话隔离与基础输入护栏的记忆增强 agent 中,明文 few-shot 记忆存在可被提取的风险",
而非论文标题暗示的"LLM agent 记忆普遍处于隐私危机中"。
